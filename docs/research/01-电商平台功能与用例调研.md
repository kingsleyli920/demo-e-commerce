# 主流电商平台功能与用例调研笔记（面向「展示 + AI 交流」Demo 的 MVP 定义）

> 文档状态：v1（2026-08-21 调研稿）｜所属：demo-e-commerce / docs/research ｜ 配套文档：[02-提效工具与 skills 调研](02-提效工具与skills调研.md)、[03-技术栈与开源参考调研](03-技术栈与开源参考调研.md)、[MVP 落地规划](../plan/01-MVP落地规划.md)

> 调研日期：2026-08-21。信息来源以 2025–2026 年公开资料为主（见文末参考资料），平台产品细节随时可能变化，落地前请以官方文档为准。
> 优先级约定：**P0 = 必做（没有就不能称为电商）**，**P1 = 重要但可后置**，**P2 = 非必要 / 锦上添花**。

## 0. 结论速览（TL;DR）

1. **电商的「不可缩水内核」只有一条链路**：商品可被找到 → 看得清（价格/规格/库存）→ 能加购 → 能结算（地址+金额计算）→ 能支付（可模拟）→ 生成订单并能看到状态。其余全部可后置。
2. **所有头部平台 2025–2026 年的 AI 能力都收敛到同一组动作**：对话式搜索/导购、商品对比、基于个人与订单的问答、加购/代下单、价格追踪与条件触发购买、售后代办。Amazon 已把 Rufus 合并成「Alexa for Shopping」并做到代买（Buy for Me）；阿里用千问 App 打通淘宝（挑选→比价→下单→支付宝付款→查物流/退换货）；京东上线独立 App「京东 AI 购」；字节让豆包在 App 内直接完成抖音商城下单支付。
3. **Agentic Commerce 在 2026 年已经从「概念」变成「协议之争」**：OpenAI/Stripe 的 ACP、Google 的 UCP + AP2、Shopify 的 Storefront MCP → UCP MCP（Catalog/Cart/Checkout/Order）、Visa Trusted Agent Protocol / Mastercard Agent Pay、Stripe Shared Payment Token。值得注意的教训：OpenAI 的 ChatGPT Instant Checkout 在 2026-03 被撤回，原因是库存、税费、价格更新、订阅与多样化履约让「代结算」远比「代发现」复杂 —— 这对 Demo 的启示是：**AI 代结算的价值在于把「购物车 + 结算 + 订单」暴露为标准工具接口（MCP/REST），而不是让模型自己算钱**。
4. **对 Demo 最有性价比的 AI 形态**：一个有工具（search/compare/cart/checkout/order/return）的导购 Agent + 一个可被外部 Agent 调用的「Storefront MCP 风格」接口。两者复用同一套 API，成本最低、可展示性最强。

## 1. 核心用户旅程（Buyer Journey）

### 1.1 分步能力与优先级

| 阶段 | 平台普遍具备的能力 | 代表性实现（平台） | 优先级 |
|---|---|---|---|
| **① 发现（首页/入口）** | 首页运营位/Banner、分类导航、「猜你喜欢」信息流、活动会场（秒杀/百亿补贴/百亿秒杀）、直播/短视频带货入口、推送/消息 | 淘宝/京东首页「猜你喜欢」；拼多多「百亿补贴」常驻入口；抖音商城的短视频/直播挂车；Amazon 首页个性化栏位；Temu 首页的签到/转盘/砍价等游戏化入口 | 首页 + 分类导航 **P0**；个性化信息流 **P1**；直播/游戏化 **P2** |
| **② 浏览 / 搜索** | 关键词搜索、搜索联想、分词与同义词、类目/品牌/价格区间/属性筛选、排序（综合/销量/价格/新品）、搜索结果商品卡（图、价、销量、店铺、标签）、搜索无结果兜底推荐、图片搜索（拍立淘/Amazon Lens）、AI 对话搜索 | 淘宝「AI 万能搜」（深度思考 / 购物偏好开关，主攻穿搭指南、送礼清单、选购攻略、口碑速览）；Amazon 把 Rufus 直接放进搜索框；Shopify 标准店铺是 Search & Discovery（预测搜索 + 筛选） | 关键词搜索 + 基础筛选排序 **P0**；联想/同义词/分词优化 **P1**；图搜 **P2**；AI 对话搜索 **Demo 定位下 P0** |
| **③ 商品详情（PDP）** | 主图/视频、标题、价格（原价/到手价/促销标签）、规格选择（SKU）、库存与「仅剩 N 件」、配送信息（发货地、预计送达、运费）、服务承诺（7 天无理由、退货包运费）、评价与问答、店铺信息、推荐搭配/相似商品、收藏/加购/立即购买、客服入口 | Amazon 的「Customers say」AI 评价摘要、「Help Me Decide」、AI 尺码推荐、Shopping Guides；京东的价格趋势 / AI 看评价；淘宝的问大家 / AI 试穿 | 图文 + 价格 + SKU 选择 + 库存 + 加购/立即购买 **P0**；评价展示 **P1**；问答、推荐、AI 摘要 **P1**；AR/试穿 **P2** |
| **④ 加购 / 收藏** | 加购（数量、SKU）、购物车按店铺分组、选中/全选、修改数量、删除、失效商品区、凑单/优惠提示、收藏夹（商品/店铺）、降价提醒 | 淘宝 2024 年第 4 次扩容至 300 件现货（+80 预售），新增分组、排序、优惠筛选；京东购物车（不同时期 120→180 件，双11 扩容）；Amazon 「Save for later」/ Wish List；Shopify 购物车是 Cart 对象 + 可选 Cart Drawer | 加购/改数量/删除/全选 **P0**；失效商品处理 **P0**（避免结算报错）；收藏 **P1**；降价提醒 **P2** |
| **⑤ 结算（Checkout）** | 选择/新增收货地址、配送方式与运费、商品清单与价格快照、优惠券/满减/积分抵扣、发票、备注、订单金额明细（商品总价-优惠+运费）、提交订单 → 生成待支付订单 | 淘宝/京东的「确认订单」页；Amazon 的 1-Click / 默认地址卡片；Shopify Checkout（Shop Pay 加速结账，Spring '26 起 Shop Pay 开放给非 Shopify 店铺） | 地址 + 金额明细 + 提交订单 **P0**；优惠券 **P1**；发票/积分/运费模板 **P2** |
| **⑥ 支付** | 多支付方式（支付宝/微信/银行卡/Apple Pay/PayPal/Shop Pay/分期 BNPL）、支付倒计时（常见 15–30 分钟未支付自动取消）、支付结果回调、支付失败重试、支付成功页 | 支付宝「AI 付」被千问 App 调用完成一键付款；Shopify Shop Pay；Amazon 默认卡 | 模拟支付（一键支付成功/失败）+ 超时取消 **P0**；多支付方式切换 UI **P1**；真实支付网关 **P2** |
| **⑦ 订单 / 物流** | 订单列表（全部/待付款/待发货/待收货/待评价/退款）、订单详情、订单状态机、取消订单、物流轨迹、确认收货、再次购买、催发货、订单搜索 | 京东自营的物流轨迹；Amazon 的 Track package、Buy Again；Shopify 的 Order status page + Shop app 追踪 | 订单列表/详情/状态 **P0**；取消订单 **P0**（最小售后）；物流轨迹（可 Mock）**P1**；再次购买 **P1** |
| **⑧ 售后 / 评价** | 申请退款/退货退款/换货、售后进度、平台介入、评价（星级+文字+图片）、追评、客服（人工/AI）、订单问答 | 2025-04-22 淘宝/拼多多/京东/抖音/快手集体调整「仅退款」：平台不再主动介入，交由商家处理；拼多多 2026 年对 AI 客服的规定（响应≤5 分钟、转人工≤2 分钟、AI 不得自动改价/承诺补偿） | 评价（发布+展示）**P1**；退款申请 + 商家审批 **P1**；换货/平台介入 **P2**；AI 客服 **Demo 定位下 P0/P1** |

| 平台 | 值得借鉴的点 |
|---|---|

## 2. 卖家 / 运营侧（Seller / Admin）

| 模块 | 平台普遍能力 | 优先级 | Demo 建议 |
|---|---|---|---|
| **商品管理** | SPU/SKU 维护、规格（颜色/尺码等销售属性）与 SKU 笛卡尔积生成、每 SKU 独立价格/库存/图片/条码、类目与属性（关键属性/非关键属性）、详情富文本、主图/视频、上下架、草稿/审核、批量导入导出 | SPU/SKU/规格/库存/上下架 **P0**；类目属性、审核、批量 **P1**；视频、多语言、多币种 **P2** | 做一个最小后台页或直接用 seed 数据 + 一个「商品编辑」页面 |
| **库存管理** | SKU 库存、可售库存 vs 锁定库存、库存预警、多仓 | 单仓 SKU 库存 **P0**；锁定库存字段 **P0**（配合下单）；多仓 **P2** | 字段 `stock` + `locked_stock` 足够 |
| **订单管理** | 订单列表/筛选、发货（填物流单号）、改地址、取消、退款审批、备注、导出 | 列表 + 发货 + 退款审批 **P1**（Demo 可用「模拟发货」按钮） | 后台一个订单列表 + 状态推进按钮即可 |
| **营销** | 优惠券（满减券/折扣券/无门槛；店铺券/商品券；领取/发放/过期）、满减/满赠、限时折扣、秒杀（库存单独、每人限购）、拼团、会员价、积分 | 优惠券（固定金额 + 门槛）**P1**；限时折扣 **P1**；秒杀/拼团 **P2** | 优惠券是 AI 场景的好素材（「有什么券可用？帮我凑单」） |
| **内容/运营位** | 首页 Banner、楼层/专题、推荐位、榜单、搜索热词 | Banner + 首页楼层配置 **P1**（Demo 可 hardcode 为 **P0 展示项**） | 用 JSON 配置首页即可 |
| **数据看板** | GMV、订单量、转化率、客单价、流量来源、商品排行、AI 渠道归因（Shopify 会在订单上标注来自哪个 AI 渠道） | **P2**；Demo 可用几张统计卡片装点 | 有 AI 渠道归因字段会很加分 |
| **客服/AI 助手** | 商家侧 AI：Shopify Sidekick（店铺问答、改商品、分群、执行后台操作、生成小应用；Sidekick App Extensions）、抖音「千川·乘方」、平台 AI 客服规则 | **P2** | 可后置，先做买家侧 AI |

## 3. 平台基础能力

| 能力 | 平台通行做法 | 优先级 | 注意事项 |
|---|---|---|---|
| 账号/登录 | 手机号验证码、第三方登录、游客浏览、登录后合并游客购物车 | 登录 **P0**（Demo 可用「一键演示账号」）；游客购物车合并 **P1** | 游客可浏览/加购，结算必须登录 |
| 地址管理 | 多地址、默认地址、省市区三级、标签（家/公司）、海外的州/邮编 | **P0**（至少能新增/选择一个地址） | 地址需在订单中做快照 |
| 搜索 | 分词（中文）、同义词、拼写纠错、筛选（类目/品牌/价格/属性）、排序、联想、热搜 | 关键词 LIKE/全文检索 + 筛选排序 **P0**；分词/同义词 **P1** | Demo 可用 PostgreSQL 全文检索 / SQLite FTS5 / pgvector 语义检索 |
| 推荐 | 猜你喜欢、相似商品、搭配购买、浏览历史 | 相似商品（同类目）**P1**；个性化 **P2** | 可用「同类目 + 价格相近」的简单规则 |
| 购物车 | 跨店分组、选中/全选、数量上下限（淘宝 300 件现货上限；单 SKU 通常有限购）、失效商品区、价格变动提示、优惠计算、合并同 SKU | 核心操作 **P0**；失效/限购 **P0**；跨店分组 **P1**（单商户 Demo 可省略） | 购物车显示实时价，订单用快照价 |
| 库存与超卖 | 三种扣减时机：下单预扣（锁库存，超时释放）/ 下单扣减 / 支付扣减；原子更新 `WHERE stock >= qty`；秒杀用 Redis 预扣 | **P0**（选「下单锁库存 + 支付确认扣减 + 超时释放」） | 见第 6 节 |
| 支付 | 多渠道、支付单独立于订单、回调幂等、对账 | 模拟支付 **P0**（支付页 → 选择方式 → 成功/失败） | 保留 `Payment` 实体，未来接真网关 |
| 通知 | 站内消息、短信、App 推送、邮件、订阅式提醒（Amazon Interests、降价通知） | 站内「消息中心」**P1**；邮件/短信 **P2** | AI 可把「条件触发」（降价/补货）作为展示点 |
| 多端 | Web/H5/小程序/App | Web 响应式 **P0** | — |

## 4. 各平台 AI 购物能力（重点）

### 4.1 平台内置 AI 助手对照（2025–2026）

| 平台 / 产品 | 上线与现状 | 具体能做什么 | 关键数据 |
|---|---|---|---|
| **Amazon Rufus → Alexa for Shopping** | Rufus 2024-02 上线；2026-05-13 与 Alexa+ 合并更名为 Alexa for Shopping，面向美国用户（App/网站/Echo Show，不需要 Prime） | 在主搜索框直接提问、商品对比（多选商品并排比较）、品类/商详 AI 概览、**价格历史（最长 1 年）+ 降价提醒 + 到价自动购买**、**定时/条件动作**（补货宠物粮、「降到 $10 就加购」）、对话式再次购买、**Buy for Me**（用默认地址和信用卡在第三方网站代买，商品数从 6.5 万增至 50 万+）、包裹追踪与订单问答、拍照搜索、找优惠、记住家庭成员/宠物/饮食偏好 | 2025 年 Rufus 服务 3 亿用户；MAU 同比 +115%，互动 +400%。同系列还有 Interests（自然语言订阅新品/补货/降价）、Review Highlights、Help Me Decide、Hear the Highlights、Shopping Guides、AI 尺码推荐 |
| **淘宝：淘宝问问 → AI 万能搜 / AI 助手；千问 App × 淘宝** | 淘宝问问 2023-09 内测；**AI 万能搜 2025 年 8 月全量**（聊天界面含「深度思考」「购物偏好」开关）；**2026-01-15 千问 App 接入淘宝闪购 + 支付宝「AI 付」**（一句话下单，400+ 办事功能）；**2026-05-11 千问与淘宝全面打通** | AI 万能搜：先搜攻略 → 按攻略筛商品 → 分析总结为几个精选推荐，主攻穿搭指南、送礼清单、选购攻略、口碑速览；AI 助手：听懂复杂需求、主动给攻略/比价/跨品类推荐；千问：用自然语言描述需求（「夏天通勤衬衫、预算 200、纯棉、浅蓝」）→ 检索 40 亿商品 → 生成多张订单卡片、跨店比价（价格/销量/评分/店铺等级）→ 生成订单 → 支付宝付款不跳转 → 查物流、退换货、联系客服；淘宝 App 同步 AI 试穿、AI 算优惠、AI 低价帮抢 | 千问 MAU 2026-02 破 3 亿；春节后 1.4 亿用户首次体验 AI 购物 |

### 4.4 Demo AI 架构建议（与 Agentic Commerce 协议对齐）

- **一套工具、两个入口**：站内导购 Agent（聊天抽屉/页面）与对外 MCP Server 共用同一组工具；命名参考 UCP/Shopify：`search_catalog`、`get_product`、`compare_products`、`create_cart/get_cart/update_cart`、`apply_discount`、`create_checkout`、`get_order`、`request_return`、`create_price_watch`。
- **模型不算钱**：价格、优惠、库存、税费、运费一律服务端计算并返回结构化结果，LLM 只负责理解意图、选择工具、解释结果 —— 这是 OpenAI 撤回 Instant Checkout 与 Shopify 强调「商家掌控结算」的共同教训。
- **代下单必须有「用户确认」节点**：Agent 生成订单预览（相当于 AP2 的 Cart Mandate），用户点击「确认并支付」（Payment Mandate），再进入模拟支付；订单记录 `channel = 'ai_assistant' | 'mcp' | 'web'` 做归因（对标 Shopify 的 AI 渠道归因）。
- **结构化商品 Feed**：商品数据字段尽量齐全（标题、品牌、类目、属性、价格、库存、图片、政策），这与 ACP Product Feed / Google Merchant Center / Shopify Catalog 的要求一致，也是 AI 回答质量的前提。

### 5.2 最小闭环描述（一个用户从进站到看到订单状态）

1. **进站**：打开首页，看到 Banner、类目导航、推荐商品楼层；可直接点进商品或使用搜索/AI 助手。
2. **找商品**：在搜索框输入「蓝牙耳机」或对 AI 说「帮我找 300 元以内适合跑步的蓝牙耳机」；得到列表（可筛类目/价格、排序）。
3. **看详情**：进入商品详情页，查看图文、价格、评价摘要；选择规格（颜色=黑、版本=标准）定位到 SKU，显示库存与到手价。
4. **加购**：点击「加入购物车」（或让 AI 代加）；购物车角标更新；进入购物车可改数量、勾选商品，看到合计。
5. **结算**：点击「去结算」→ 未登录则一键演示登录 → 订单确认页：选择/新增地址、查看商品快照与金额明细（商品总额 − 优惠 + 运费）→「提交订单」。
6. **下单**：服务端校验价格与库存、锁定库存、生成 `Order(status=PENDING_PAYMENT)` + `OrderItems`（含价格快照）+ `Payment(status=INIT)`，返回订单号并进入支付页（含 15 分钟倒计时）。
7. **支付**：选择「模拟支付」→ 点击「支付成功」→ 回调更新 `Payment=SUCCESS`、`Order=PAID`、库存正式扣减；点击「支付失败」则停留可重试；超时则订单自动 `CANCELLED` 并释放库存。
8. **看订单**：跳转「我的订单」→ 订单详情显示「已支付/待发货」；后台点「模拟发货」后状态变为「已发货」（可显示 Mock 物流轨迹）→ 用户「确认收货」→「已完成」；随时可对 AI 问「我的耳机到哪了？」得到基于订单数据的回答。

### 6.2 关键关系

- Category 1—N Product；Product 1—N SKU；Product 1—N ProductAttribute；SKU 的 `spec_json` 必须是该 Product 属性值的合法组合且组合唯一。
- User 1—1 Cart；Cart 1—N CartItem（CartItem 唯一键 = cart_id + sku_id，重复加购合并数量）。
- User 1—N Order；Order 1—N OrderItem；Order 1—N Payment（允许多次支付尝试，但只能有一个 SUCCESS）。
- OrderItem —1 SKU（引用），但展示用字段全部来自快照而非实时 SKU。
- Review —1 OrderItem（防刷评）。
- Coupon N—N User（通过 UserCoupon）；Order —0..1 UserCoupon。

### 6.3 需要注意的坑

| 坑 | 说明 | 建议做法 |
|---|---|---|
| **SKU 规格组合** | 规格维度笛卡尔积可能很大；有的组合不售卖；属性顺序不一致导致重复 | 后台按勾选生成 SKU，允许删除不售卖组合；`spec_json` 按属性顺序规范化后做唯一索引；前端用「已选规格 → 可选规格」联动 |
| **价格快照** | 下单后商品改价/改名/下架不能影响已下单；购物车却要显示最新价 | OrderItem 存 `unit_price_snapshot/title/spec/image`；Order 存 `address_snapshot`；购物车页若价格变动给出提示 |
| **库存扣减时机** | 三种方案：下单扣（最不会超卖，但恶意占库存）/支付扣（可能超卖）/下单预扣 + 支付确认 + 超时释放（主流） | 推荐第三种：提交订单 `UPDATE sku SET locked_stock = locked_stock + ? WHERE stock - locked_stock >= ?`；支付成功 `stock -= q, locked_stock -= q`；取消/超时 `locked_stock -= q`；每步写 InventoryLog |
| **超卖与并发** | 并发下单靠「先查后改」一定会超卖 | 用带条件的原子 UPDATE 或乐观锁 `version`；秒杀可用 Redis 预扣；Demo 至少要有原子 UPDATE |
| **订单状态机** | 状态随意跳转会导致脏数据 | 显式定义：PENDING_PAYMENT → PAID → SHIPPED → COMPLETED；PENDING_PAYMENT → CANCELLED（用户取消/超时）；PAID → REFUNDING → REFUNDED（P1）；每次迁移校验前置状态并记录时间戳 |
| **支付幂等** | 回调可能重复/乱序 | Payment 以 `transaction_no` 幂等；订单已 PAID 的重复回调直接返回成功 |
| **待支付超时** | 需要定时关闭并释放库存 | `expire_at` + 定时任务（或访问时惰性检查） |
| **金额精度** | 浮点误差 | 金额用整数「分」或 DECIMAL(12,2) |
| **购物车失效项** | SKU 下架/售罄/商品删除后购物车残留 | 查询购物车时 join SKU 实时状态，标记 `invalid` 并禁止勾选；结算时再次校验 |
| **限购与上限** | 单 SKU 限购、购物车总件数上限（淘宝 300） | CartItem 数量校验 `min(库存, 限购)`；购物车总条数上限可设 100 |
| **地址与运费** | 运费依赖地址与商品 | Demo 固定运费/包邮门槛即可，但把计算放在服务端的「结算预览」接口 |
| **优惠券分摊** | 整单券如何分摊到 item（退款时用） | MVP 可只记录整单 discount；若做退款再按金额比例分摊 |
| **AI 渠道归因** | 后续分析哪些订单来自 AI | Order.channel 字段从第一天就加上 |
| **软删除** | 商品/SKU 被历史订单引用 | 商品/SKU 用状态位而非物理删除 |
