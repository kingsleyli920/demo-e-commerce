# P0 完成标准与测试矩阵

> 每个 P0 功能 = 验收标准（可逐条勾选）+ 自动化测试（类型 / 文件 / 用例）+ 手动演示点。状态：v1.0（2026-08-22）。
> 测试分层：**unit/integration**（Vitest，直连测试库 `shop_test`，每个文件前 truncate + 最小 seed）、**e2e**（Playwright，对 `pnpm dev` + 完整 seed）、**CI**（GitHub Actions）。文件位置：`tests/unit/**`、`tests/e2e/**`。

## 测试基础设施（P0-9 的前置）

| 项 | 要求 |
|---|---|
| 测试库 | `DATABASE_URL_TEST=postgres://shop:shop@localhost:5432/shop_test`；`pnpm test:unit` 前自动 `drizzle-kit migrate` 到测试库 |
| 数据工厂 | `tests/factories.ts`：`createUser / createProductWithSkus / createAddress / placeTestOrder` |
| 脚本 | `pnpm test:unit`（Vitest）、`pnpm test:e2e`（Playwright chromium）、`pnpm test`（两者）、`pnpm lint`、`pnpm typecheck` |
| CI | `.github/workflows/ci.yml`：services `postgres:16` → install → lint → typecheck → migrate → unit → build → e2e；PR 必须绿 |
| 覆盖目标 | service 层语句覆盖 ≥ 80%（`src/server/services/**`），不追求 UI 覆盖率 |

## P0-2 商品目录与搜索

**验收标准**
1. 首页展示 2 级类目入口与 ≥ 12 个上架商品卡（图、标题、最低价、销量）。
2. `/search?q=` 按标题/品牌/副标题 `ILIKE` 匹配，大小写不敏感；空关键词返回全部上架商品。
3. 类目筛选包含子类目商品；价格区间按 `min_price` 过滤（单位分，参数为元）。
4. 排序：综合（默认：销量降序→新品）、销量、价格升/降、新品；切换排序保持其它条件。
5. 分页 20/页，显示总数与页码；超出范围返回空页而非报错。
6. 下架（`status != on`）商品不出现在任何列表/搜索/详情（直接访问详情返回 404 页）。
7. 无结果时显示空态与「清除筛选」。

**验收标准**

## P0-4 库存

**验收标准**
1. `skus.stock`（实物）与 `skus.locked_stock`（已锁）分离；可售 = stock − locked_stock。
2. 提交订单对每个 SKU 执行条件原子更新锁定；任一 SKU 不足 → 整单失败、已锁定的回滚、返回具体哪个 SKU 不足。
3. 支付成功：`stock -= q, locked_stock -= q`；取消/超时：`locked_stock -= q`。
4. 每次变动写 `inventory_logs(sku_id, change, type ∈ {lock, unlock, deduct}, ref_order_id)`。
5. **并发**：库存 10 的 SKU 并发 50 次各买 1 件，恰好 10 单成功，最终 `stock=10, locked_stock=10`，支付后 `stock=0, locked=0`，无负数。

**自动化测试**
| 类型 | 文件 | 用例 |
|---|---|---|
| unit | `tests/unit/inventory.test.ts` | 锁定成功/不足失败；多 SKU 其中一个不足整单回滚；支付扣减；取消释放；日志条数与类型；可售不可为负 |
| unit | `tests/unit/inventory.concurrency.test.ts` | `Promise.all` 50 次 `placeOrder` 同 SKU（stock 10）→ 成功 10 / 失败 40 / 库存字段正确 / 日志 10 条 lock |
| e2e | `tests/e2e/stock-guard.spec.ts` | 后台把 SKU 库存改为 1 → 买家 A 下单成功 → 买家 B 同 SKU 下单提示库存不足 |

## P0-5 购物车

**验收标准**
1. 加购同 SKU 合并数量；不同 SKU 各一行；`(cart_id, sku_id)` 唯一。
2. 数量步进/输入受限：1 ≤ qty ≤ min(可售库存, 99)；超限时提示并钳制。
3. 删除单行；勾选/全选/反选；合计只统计已勾选且有效项。
4. 失效项（SKU 下架或可售为 0）单独分区展示「已失效」，不可勾选、不计入合计，可删除。
5. 价格取 SKU 实时价；与加购时不同则在行内提示「价格有变动」。
6. 条目 > 50 时拒绝新增并提示。
7. 头部角标 = 有效条目数量之和（或行数，二选一并写进 README）。

**自动化测试**
| 类型 | 文件 | 用例 |
|---|---|---|
| unit | `tests/unit/cart.test.ts` | 加购合并；数量上限钳制（库存 / 99）；删除；勾选/全选；失效项标识与不计入合计；50 条上限；合计计算；价格变动标记 |
| e2e | `tests/e2e/cart-ops.spec.ts` | 两次加购同 SKU 数量为 2；改数量到超库存被钳制并提示；取消勾选后合计变化；删除行；后台下架该 SKU 后购物车显示失效且不可勾选 |

## P0-6 Mock Checkout（地址 / 结算 / 下单 / 支付 / 超时）

**验收标准**
1. 地址：新增/编辑/删除/设默认；省市区用静态 JSON；至少一个地址才能结算。
2. 结算预览（服务端）：商品合计、运费（≥ 9900 分免，否则 1000 分）、应付；含失效项时拒绝并提示回购物车处理。
3. 提交订单：再次校验价格与可售库存 → 锁库存 → 生成 `orders(PENDING_PAYMENT, expire_at = now + 15min)` + `order_items` 快照 + `payments(INIT)` → 删除购物车中对应已勾选项 → 跳转 `/pay/[orderNo]`。
4. 订单号唯一可读（`ORD` + 时间戳 + 4 位随机）；`orders.channel = web`。
5. 支付页：倒计时、「模拟支付成功」「模拟支付失败」；成功 → `payments=SUCCESS`、`orders=PAID`、扣库存 → 跳订单详情；失败 → 停留可重试。
6. 回调幂等：重复 `transaction_no` / 已 PAID 订单重复回调均返回成功且不重复扣库存；已 CANCELLED 订单回调被拒绝。
7. 超时：到期订单在被读取时（订单详情/列表/支付页）惰性置为 CANCELLED 并释放库存；`POST /api/cron/expire-orders`（需 `CRON_SECRET`）与后台按钮可批量处理。
8. 立即购买走同一结算流程（仅该 SKU，不动购物车）。

**自动化测试**
| 类型 | 文件 | 用例 |
|---|---|---|
| unit | `tests/unit/address.test.ts` | CRUD；设默认会取消其它默认；删除默认后无默认 |
| unit | `tests/unit/checkout.preview.test.ts` | 运费边界（9899 / 9900）；应付 = 合计 + 运费；含失效项拒绝；未勾选项不计入 |
| unit | `tests/unit/order.place.test.ts` | 成功建单：状态/过期时间/快照字段/订单号格式/支付单 INIT/购物车项被移除/库存锁定；价格变动仍以服务端为准；库存不足失败且无残留订单；立即购买不影响购物车 |
| unit | `tests/unit/payment.mock.test.ts` | 成功 → PAID + 扣库存 + paid_at；失败 → 仍 PENDING 可重试；同 transaction_no 重复幂等；已 PAID 重复回调幂等；已 CANCELLED 拒绝 |
| unit | `tests/unit/order.expire.test.ts` | 过期订单读取时自动取消并释放；未过期不动；批量处理端点返回数量；无 secret 返回 401 |
| e2e | `tests/e2e/checkout-pay.spec.ts` | 无地址 → 提示新增 → 新增后结算 → 提交 → 支付页倒计时 → 成功 → 订单详情「待发货」且库存数在详情页减少 |

## P0-7 订单

**验收标准**
1. `/orders` Tab：全部/待付款/待发货/待收货/已完成/已取消，计数正确，按创建时间倒序。
2. 详情：订单号、状态、状态时间线（创建/支付/发货/完成/取消时间）、商品快照列表、地址快照、金额明细（合计/运费/应付）、操作按钮按状态显示。
3. 取消：仅 `PENDING_PAYMENT` 可取消 → `CANCELLED` + 释放库存；其它状态按钮不出现且服务端拒绝。
4. 确认收货：仅 `SHIPPED` → `COMPLETED`；其它状态拒绝。
5. 历史订单不受商品改价/下架影响（展示快照）。
6. 只能查看自己的订单（他人订单号 → 404）。

## P0-10 AI 协作留痕

**验收标准**
1. 单一 `dev` 分支；提交遵循 Conventional Commits 并带里程碑 scope（`feat(m2):` / `test(m3):` / `docs(m1):` …）；每个里程碑结束有一条 `chore(mN): milestone N 验收通过（测试 X/Y，耗时 Zh）`；service 层功能先有 `test(mN):` 提交再有 `feat(mN):` 提交；每条提交含 `Co-Authored-By: Claude …`。
2. `AI_WORKFLOW.md` 每个里程碑段已随 `chore(mN)` 提交填齐（关键 Prompt、模型选择、Skills/Plugins/MCP、人工决策、失败与恢复、人工介入次数、耗时、测试结果），总览表数字可核；第 3 节独立 Review、第 4 节 M5 门槛检查在 P0 完成后填写。
3. `docs/adr/0001-范围收敛.md`、`0002-技术栈.md`、`0003-库存与订单规则.md` 存在。
4. `CLAUDE.md`（< 150 行）+ `.claude/rules/{server,ui,tests}.md` + PostToolUse 格式化 hook + PreToolUse 危险命令拦截 hook + `code-reviewer` 只读 subagent。
5. P0 完成后：独立 Review（`/code-review` 或 `code-reviewer`）无 Critical/High 遗留；tag `p0-done`；Final PR `dev → main`（描述含范围 / 验收勾选 / 测试输出 / AI_WORKFLOW 链接 / 录屏链接）。
6. M4 产出 **3–5 分钟关键流程录屏**（主路径 + 库存并发 + 30 秒提交历史/AI_WORKFLOW 速览）与若干截图，放 `docs/screenshots/`（或 README 链接）；不做全程录屏；不引入 OpenSpec。
